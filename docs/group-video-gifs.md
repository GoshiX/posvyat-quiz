# Анимации групп из видео

`tools/group-video-timings.json` задаёт фрагменты 27 групп: всего 397 секунд, по 11–17 секунд на группу. Фрагменты склеиваются **в порядке списка**, даже если следующий начинается раньше предыдущего. Например, `[9, 13], [48, 53], [18, 23]` нельзя сортировать по времени. Для Б05-605 используются уточнённые интервалы `[37, 40], [81, 89]`.

Результат для организатора — зацикленный GIF и MP4 с тем же монтажом, без звука. Для карточек голосования создаётся отдельный анимированный WebP: он хранит больше цветов и обычно заметно меньше GIF. Карточка получает адрес WebP в `mediaUrl`; GIF и MP4 остаются доступными для просмотра и передачи отдельно. Скрипты ниже готовят файлы локально и сами не загружают их в Object Storage.

## Зависимости и рабочие каталоги

Команды выполняются из корня проекта. Нужен Python 3.11+; загрузчик использует `hashlib.file_digest`, появившийся в 3.11. Для рендера нужны доступные в `PATH` `ffmpeg` и `ffprobe`; сборка FFmpeg должна поддерживать `libx264`, GIF, PNG и `libwebp_anim`. У рендера и загрузчика HTTP-диапазонов нет сторонних зависимостей Python; для пакетной загрузки нужен `gdown`.

```sh
python3 -m venv .venv
.venv/bin/python -m pip install gdown
ffmpeg -version
ffprobe -version
```

Рабочие файлы текущей подготовки:

```text
data/group-video-preparation/
  manifest.json
  downloads.json
  source/                       исходные MP4/MOV
  rendered/                     GIF, MP4, WebP и отчёты
```

Каталог `data/` исключён из Git. Сохраняйте исходники, manifest и результаты вместе: для проверки и продолжения рендера нужны исходные файлы и индивидуальные JSON-отчёты.

## Manifest и соответствие групп

Файл с таймингами содержит только `number` и `segments`. Перед загрузкой и рендером его дополняют явным соответствием файла и группы. Рабочий manifest `data/group-video-preparation/manifest.json` выглядит так:

```json
{
  "version": 1,
  "groups": [
    {
      "id": "Б05-605",
      "number": "Б05-605",
      "driveId": "EXACT_GOOGLE_DRIVE_FILE_ID",
      "input": "source/Б05-605.mp4",
      "segments": [[37, 40], [81, 89]]
    }
  ]
}
```

- `version` — число `1`, обязательно для рендера.
- `groups` — непустой массив. `id`, `number`, `input` — непустые строки; `id` уникален. Для загрузчика `number` также должен быть уникальным, а у каждой записи обязателен `driveId`.
- `id` — стабильный идентификатор результата. В текущем manifest он равен номеру группы; это **не UUID группы из базы приложения**. При публикации сопоставляйте его с записью приложения по полному `number`.
- `driveId` — точный ID публично доступного файла Google Drive, нужен только загрузчикам. Путь к папке и частичное совпадение имени файла не заменяют ID.
- `input` — абсолютный путь либо путь относительно каталога manifest, а не текущего рабочего каталога. Расширение может быть `.mp4`, `.mov` или другим поддерживаемым FFmpeg видеоформатом.
- `segments` — непустой массив пар `[start, end]` в секундах от начала видео. Разрешены дробные секунды; требуются конечные числа и `0 <= start < end`. `end` не должен выходить за длительность исходника: рендер отклоняет такой фрагмент без молчаливого обрезания.

`sourceFolder`, `notes` и другие дополнительные поля не управляют обработкой. Для нового набора файлов сначала проверьте полное соответствие `number → driveId → input`; загрузчики не определяют его автоматически.

## Загрузка исходников

Пакетная загрузка всех записей manifest:

```sh
.venv/bin/python tools/download_group_videos.py \
  data/group-video-preparation/manifest.json --jobs 3
```

`--jobs` допускает 1–4, по умолчанию 3. Для каждого отсутствующего файла загрузчик вызывает `gdown` без cookies с `resume=True`, до четырёх попыток с паузами 1, 2 и 4 секунды. Незавершённая загрузка использует имя `<input>.download`; служебные файлы возобновления `gdown` также нужно сохранять. После успешного `ffprobe` временный файл переименовывается в `input`.

Для продолжения повторите ту же команду. Уже существующие `input` не скачиваются: они проверяются через `ffprobe`, затем хешируются. Загрузчик не сравнивает их с удалённым Drive-файлом или предыдущим SHA-256. Повреждённый существующий `input` сам не перекачивается; после проверки причины уберите именно этот файл из рабочего пути и повторите загрузку.

`downloads.json` записывается рядом с manifest после каждого завершения. Формат — `{"groups": [...]}` в порядке manifest. У успешной записи: `number`, `driveId`, абсолютный `input`, `status: "downloaded"`, `bytes`, `sha256`, `seconds`, `duration`, `width`, `height`, `codec`. Ошибка имеет `status: "error"` и `error`; ещё не завершённая запись — `status: "pending"`. Код выхода: 0 при успехе всех файлов, 1 при ошибке хотя бы одного.

### Загрузка одного большого файла HTTP-диапазонами

Если обычная загрузка прерывается, для конкретного файла можно использовать отдельный загрузчик. Подставьте проверенный Drive ID из manifest:

```sh
.venv/bin/python tools/download_drive_ranges.py \
  EXACT_GOOGLE_DRIVE_FILE_ID \
  data/group-video-preparation/source/Б05-605.mp4 --jobs 6
```

`--jobs` допускает 1–8, по умолчанию 6. Файл запрашивается блоками по 16 МиБ; обязательны HTTP 206, точный `Content-Range` и длина каждого блока. У каждого запроса до четырёх попыток с паузами 1, 2 и 4 секунды; таймаут запроса — 90 секунд.

Для продолжения незавершённой загрузки повторите команду с теми же ID и путём. Сохраняйте **оба** файла: `<output>.ranges` и `<output>.ranges.json`. Журнал хранит `driveId`, общий размер `bytes`, `chunkSize` и `parts`, где ключ — начальное смещение блока в байтах, значение — SHA-256. Совпадение блока проверяется перед повторным использованием. Возобновление применимо, пока исходный Drive-файл не меняется: журнал не хранит версию или ETag удалённого файла.

После успеха `.ranges` атомарно переименовывается в конечный файл, а в stdout выводятся путь, размер и SHA-256. Этот загрузчик не проверяет видео через `ffprobe` и не обновляет `downloads.json`. Проверьте результат или повторите пакетный загрузчик, который проверит готовый `input`:

```sh
ffprobe -v error -show_streams -show_format -of json \
  data/group-video-preparation/source/Б05-605.mp4
```

После успешного завершения повторная команда диапазонного загрузчика начнёт скачивание заново: существующий конечный файл он не использует. Не запускайте два загрузчика одновременно для одного пути.

## Рендер GIF и склеенного MP4

Текущий профиль: 30 кадров/с, длинная сторона до 480 пикселей. Рендер всех групп:

```sh
.venv/bin/python tools/prepare_group_gifs.py \
  data/group-video-preparation/manifest.json \
  --output data/group-video-preparation/rendered \
  --fps 30 --max-side 480 --jobs 2
```

Для проверки или повторной обработки отдельных групп:

```sh
.venv/bin/python tools/prepare_group_gifs.py \
  data/group-video-preparation/manifest.json \
  --output data/group-video-preparation/rendered \
  --fps 30 --max-side 480 --jobs 1 \
  --group Б05-605 --group Б05-612
```

`--group` повторяется и принимает точный `id` либо однозначный полный `number`. Неоднозначный номер отклоняется; используйте уникальный `id`. `--jobs` допускает 1–8, по умолчанию 1. Каждый процесс FFmpeg использует один поток; увеличение `--jobs` одновременно увеличивает нагрузку и временное дисковое пространство.

Каждый фрагмент отдельно приводится к 30 кадрам/с и H.264, затем фрагменты склеиваются без звука, субтитров и метаданных. Корректируются поворот и соотношение пикселей, пропорции сохраняются; размеры чётные для H.264. GIF строится из полученного MP4 с собственной палитрой и бесконечным повтором. Если результат не помещается в ограничения, уменьшаются разрешение и палитра, но частота кадров самопроизвольно не снижается.

**30 FPS в GIF.** GIF хранит задержки в сотых долях секунды, поэтому одинаковые интервалы по 33⅓ мс записать нельзя. При номинальных 30 FPS FFmpeg чередует задержки **30 и 40 мс**, сохраняя средний темп. Постоянные 40 мс дали бы 25 FPS. Точность границ нарезки ограничена сеткой 1/30 секунды; проверка длительности допускает до `число_фрагментов / 30 + 0,02` секунды для MP4 и ещё `1 / fps + 0,02` для GIF.

`--fps` управляет **GIF**. Промежуточный и итоговый MP4 всегда имеют 30 кадров/с; WebP ниже наследует монтаж MP4. Для текущей задачи оставляйте `--fps 30`.

### Файлы результата и продолжение

Имена имеют вид `<безопасный-number>--<первые-12-символов-SHA256-id>`. Для каждой группы создаются `.gif`, `.mp4` и `.json`. JSON содержит `id`, `number`, `input`, `segments`, `requested_duration_seconds`, `input_sha256`, `fingerprint`, настройки `renderer` и `render_settings`, `status: "ok"`, а также объекты `gif` и `mp4` с `path`, `sha256`, `bytes`, `duration_seconds`, `width`, `height`, `frames`, `decoded_pixels`. Для GIF указан `loop: 0` — бесконечный повтор.

Сводный `results.json` атомарно обновляется после каждой группы и содержит `version`, путь `manifest`, `settings`, `groups`. Ошибка группы записывается как `status: "failed"` с полем `error`. Код выхода рендера: 0 — все выбранные группы готовы; 1 — есть ошибки групп; 2 — ошибка аргументов, manifest или запуска инструмента.

После остановки повторите команду с теми же параметрами. Повторное использование требует совпадения SHA-256 исходника, порядка и границ фрагментов, настроек, версии рендера и строки версии FFmpeg. Дополнительно проверяются SHA-256 и параметры обоих выходных файлов; в консоли появляется `reused`. Недостающие, изменённые и повреждённые результаты создаются заново. При неудачном повторном рендере прежние GIF, MP4 и индивидуальный JSON этой группы удаляются, чтобы старый файл не выглядел успешным результатом.

Отдельные фрагменты внутри прерванной группы не сохраняются для продолжения: эта группа рендерится с начала. После принудительного завершения могут остаться скрытые временные каталоги; это не готовые результаты. Запуск с `--group` записывает в `results.json` только выбранные группы. Чтобы вернуть полный сводный отчёт, повторите команду без `--group`; готовые файлы будут проверены и использованы повторно. Не запускайте два рендера с одним выходным каталогом одновременно.

## WebP для карточек

После завершения GIF/MP4:

```sh
.venv/bin/python tools/prepare_card_webp.py \
  data/group-video-preparation/rendered
```

Скрипт читает индивидуальные `*--*.json` со `status: "ok"`, проверяет SHA-256 MP4 и создаёт рядом анимированный `.webp`, `.webp.json`, общий `webp-manifest.json` и страницу `index.html` со ссылками на GIF и MP4. В manifest WebP — объект `{"groups": [...]}`; записи содержат `id`, `number`, `path`, `sha256`, `settings`, выбранный `quality`, `nominal_fps`, `segments`, `width`, `height`, `frames`, `duration_ms`, `delays_ms`, `loop`, `bytes`, `decoded_pixels`.

WebP создаётся **из MP4**, сохраняя больше цветовой информации, чем повторное перекодирование GIF. Длинная сторона — до 640 пикселей без увеличения исходного монтажа; при профиле MP4 до 480 пикселей WebP также не превысит 480. Кодировщик пробует качество 70, 60 и 50 до достижения 6 МиБ, сохраняет бесконечный повтор и проверяет число кадров, декодируемые пиксели и отклонение длительности не более 80 мс. Здесь нет аргументов для настройки качества или размеров.

Для продолжения повторите команду. При совпадении подписи настроек, SHA-256 MP4 и SHA-256 WebP существующий результат используется повторно после проверки контейнера. Скрипт останавливается на первой ошибке, поэтому неполный каталог сначала нужно дорендерить. Итоговые manifest и HTML появляются только после успешной обработки всего каталога; готовые WebP отдельных групп сохраняются и используются при следующем запуске.

Просмотр готовой галереи локально:

```sh
.venv/bin/python -m http.server 8081 --bind 127.0.0.1 \
  --directory data/group-video-preparation/rendered
```

Откройте `http://127.0.0.1:8081/`. Это локальный просмотр; команда не публикует файлы в приложении или S3.

## Реальные ограничения и публикация

Ограничения экспорта GIF и загрузки в приложение различаются:

| Параметр | Экспорт GIF | WebP из MP4 | Загрузка изображения через приложение |
| --- | --- | --- | --- |
| Размер файла | до 67 108 863 байт, почти 64 МиБ | до 6 291 456 байт, 6 МиБ | вход до 10 485 760 байт, 10 МиБ; выход анимации до 6 МиБ |
| Кадры | до 600 | до 600 | до 600 |
| Сумма декодируемых пикселей | до 80 000 000 | до 80 000 000 | до 80 000 000 |
| Длинная сторона | до 640, текущий запуск до 480 | до 640 и без увеличения MP4 | карточки/логотип до 960, иконки до 384 |
| Длительность | ограничивается кадрами и FPS | ограничивается кадрами MP4, 30 FPS | до 120 секунд |
| Время обработки | отдельного таймаута нет | отдельного таймаута нет | таймаут Sharp 30 секунд на обработку |

`decoded_pixels = width × height × frames`, а не размер сжатого файла. Например, 480 × 270 × 510 = 66 096 000 пикселей. При 30 FPS лимит 600 кадров допускает около 20 секунд; текущие монтажи до 17 секунд дают не более 510 кадров до поправок округления. Для длинного монтажа уменьшение GIF FPS не увеличивает лимит кадров WebP, который строится из MP4 с 30 FPS.

Экспортные аргументы `--max-side`, `--max-frames`, `--max-pixels`, `--max-bytes` можно уменьшать; превышать указанные максимумы нельзя. `--fps` должен быть больше 0 и не больше 30. У GIF нет отдельного лимита в 10 МиБ: большой экспортированный GIF может корректно пройти рендер, но не пройти загрузку через админку. Для карточек используйте WebP.

В админке настройте и включите «Хранилище изображений», затем загрузите подготовленный WebP в поле изображения нужной карточки группы и сохраните группу. Сервер заново проверяет и обрабатывает изображение; при включённом хранилище возвращается публичный адрес `https://storage.yandexcloud.net/<bucket>/quiz/<uuid>.webp`. В карточке должен сохраняться именно полученный адрес. Загрузка и сохранение карточки — отдельные действия; локальные GIF/MP4 и генерация галереи сами не меняют `mediaUrl`.

При пакетной публикации заранее подготовленных WebP напрямую в S3 сохраняйте соответствие полных номеров групп с UUID приложения, MIME `image/webp` и публичную доступность каждого объекта; затем обновляйте `mediaUrl` соответствующих карточек. Ограничения HTTP-загрузки приложения не выполняются автоматически при прямой записи в S3 — их обеспечивает подготовка и проверка WebP. Существующие поля группы нужно сохранять при обновлении. Настройка бакета и ключей описана в [инструкции Object Storage](yandex-storage-setup.md).

## Проверка инструментов

Тесты рендера создают небольшие видео локально и проверяют порядок фрагментов, границы, поворот, 30 FPS GIF с задержками 30/40 мс, лимиты пикселей, восстановление повреждённых результатов и выбор группы. Сетевые загрузки в них не выполняются.

```sh
.venv/bin/python -m pip install pytest
.venv/bin/python -m pytest -q tests/test_prepare_group_gifs.py
node --test server/media.test.mjs
```
